# App audit — 2026-09-18

Whole-app pass for "what is not working", taken on `main` at `89f6caf`
(the merge of #379). Evidence was gathered on 2026-09-18 from four places:
the repository, this repo's own CI history on GitHub, the **live** Supabase
project (`ovscskaijvclaxelkdyf`) probed as the anon role, and the published
frontend at `laha-arabic.lovable.app`.

**Nothing has been fixed.** Every item names the layer that owns it —
**deploy**, **edge function**, **RLS**, **storage**, **frontend**,
**domain logic**, **content** or **guard** — and is marked CONFIRMED (the
code or the live response was read) or SUSPECTED (reasoned, not reproduced).

One item, **D4**, was marked CONFIRMED, challenged in review, verified
against the callers and **withdrawn**. It is left in place with the
refutation rather than deleted, because the wrong reasoning is reachable
from the module's docstring and the next reader should meet the answer
rather than the trap.

The finding that organises all the others: **every automated gate this repo
has is green, and almost nothing below is the kind of thing they can see.**
The four CI jobs test the repository. They do not test the deployment, they
do not evaluate RLS semantics, several guards check shape rather than
behaviour, and none of them can see production data.

## A. Production is running older code than this repository

This is the spine of the audit. Two independent delivery gaps — edge
functions and the frontend — plus the marker that was built to detect the
first one, currently blind.

### A1 — CI has never once deployed an edge function — deploy — CONFIRMED

The `Deploy edge functions` job (`.github/workflows/ci.yml:272`) has run on
every `main` push since the workflow was added. I fetched and parsed the job
log for all **234** such runs, 2026-07-31 to 2026-09-18:

- runs where the deploy step actually ran: **0**
- runs that logged "these edge functions were NOT deployed": **27**
- distinct functions named across those: **81**

`SUPABASE_ACCESS_TOKEN` has never been set, so `ci.yml:350` takes the skip
branch every time. The job's own comment explains why it is a warning rather
than a failure, and that reasoning is sound — a Lovable Cloud project cannot
mint the token, and a permanently red `main` would be worse. But the
consequence is that **the automated path has never worked at all**, which is
a different thing from "it occasionally skips".

The most recent merge is a live example: #379 ("Let a transcriber correct a
video's title") left `transcript-review` and `resync-transcript-timing`
behind. The 81 also include `create-checkout`, `customer-portal`,
`check-subscription`, `access-credentials` and `process-approved-video`.

### A2 — Functions do reach production by hand, but not reliably current — deploy — CONFIRMED

Correcting an assumption that A1 invites: I POSTed all 119 deployed function
names against the live project. **Zero 404s.** Distribution: 96×401, 13×403,
7×400, 2×500, 1×200. So someone deploys them out of band, and
`QA_MAP.md`'s `persist-video-thumbnail` **NOT DEPLOYED (404)** annotation —

deployed billing code is behind the repository, on the one path where a

### B3 — `tutor-audio-clips` and `meme-uploads` are public and enumerable — storage — CONFIRMED

`20260529122406_84f88330-…sql:64-67` grants `anon, authenticated` a
`storage.objects` SELECT covering
`('avatars','meme-uploads','flashcard-images','flashcard-audio','tutor-audio-clips','audio')`,
and `20260209171143_…sql:54` creates `tutor-audio-clips` with `public = true`.
Objects are written at `<auth.uid()>/<file>` (`useTutorUpload.ts:59-78`).

A SELECT policy on `storage.objects` is what the Storage list API checks, so
with the publishable key alone an unauthenticated caller can `list('')` to
enumerate user-id folders, `list('<uid>')` for filenames, and fetch each
object. The contents are learners' recorded tutoring sessions — private
conversation audio — and their uploaded memes/screenshots, keyed to a stable
user id. Both migrations are Lovable-authored, so this is the live state.

### B4 — `user_concept_mastery` is client-writable — RLS — CONFIRMED (mechanism), SUSPECTED (exploitable today)

CLAUDE.md names this one of the three tables where "clients read their own
rows under RLS but writes go through edge functions under the service role,
so nobody can post themselves a score".

`20260731120000_concept_mastery_hardening.sql:62-75` recreates
`"Users insert own mastery"` (INSERT, `WITH CHECK auth.uid() = user_id`) and
`"Users update own mastery"`, then at `:84-89` comments that writes all go
through the service role and issues `GRANT SELECT` — **without a REVOKE**.
Compare `learner_errors`, where the author did revoke
(`20260726140000_owned_table_constraints.sql:52-53`).

I probed the live project to settle the half that was uncertain. An anon
INSERT of `{}` into each of the three tables returns:

```
42501  new row violates row-level security policy for table "user_concept_mastery"
42501  new row violates row-level security policy for table "learner_errors"
42501  new row violates row-level security policy for table "learner_ai_memory"
```

All three reach the **policy** check rather than being refused at the
privilege check ("permission denied for table …"), which confirms the INSERT
privilege is granted on all three. `learner_errors` and `learner_ai_memory`
are still safe because they have no INSERT policy at all, so the check can
never pass. `user_concept_mastery` has a permissive own-row one. Anon fails
only because `auth.uid()` is null; an authenticated learner would satisfy it.

Remaining uncertainty is narrow — whether some out-of-band change revoked it
since — and one authenticated INSERT would close it. Note that
`contract/prelude.sql` carries no `ALTER DEFAULT PRIVILEGES`, so the replay,
`qa/output/schema/rls-tables.txt` and QA_MAP's grant column are all blind to
this whole class.

`customer-portal` → `500 {"error":"Authentication error: invalid claim…"}`

## D. Domain-logic defects

### D1 — A review can be scheduled with `intervalDays = 0` — domain logic — CONFIRMED

`spacedRepetition.ts:481` is `newInterval = Math.round(newStability *
intervalFactor)` with **no floor**. The first-exposure branch 30 lines above
(`:448`) *does* have one: `Math.max(rating === 'easy' ? 4 : 1, …)`. The clamp
below only fires `if (newInterval >= 1)` — correctly, because the learning
steps are legitimate sub-day constants — so a rounded-to-zero interval passes
straight through to `nextReviewAt = now + 0ms`.

`retentionFactor(0.97)` is 0.2228, and `desired_retention` is selectable up
to 0.97 in Settings, so any card whose new stability is ≤ ~2.2 days schedules
to zero: most young cards, and every card just out of relearning. The card is
written back due immediately, renders "< 1m" on **Good**, and the session
re-serves it indefinitely. Reachable at the 0.9 default too, for stability
below 0.5 (`MIN_STABILITY` is 0.1).

`spacedRepetition.test.ts:342` exercises `desiredRetention: 0.97` only on a
high-stability card, so the suite never reaches this.

### D2 — No maximum interval — domain logic — CONFIRMED

Same line. `MAX_STABILITY` is 36500 but the *interval* is unbounded:
36500 × `retentionFactor(0.7)` (9.288) × the 1.5 calibration ceiling ≈
**508,000 days**. Anki's 36500-day interval cap has no counterpart here. A
card that reaches it leaves the learner's schedule with no error anywhere.

### D3 — Microphone denial is silent on the SRS card — frontend — CONFIRMED

`PronunciationButton.tsx:121-123` is `catch { console.error(…) }` — no toast,
no state change, no disabled state, so the button looks dead. The identical
bug was found and fixed at the other recorder, and
`PronunciationPractice.tsx:199-206` still carries the comment "Silence here
left the record button looking dead". This call site was missed.

The same component has **no unmount cleanup** for its recorder or
MediaStream (compare `SetPhrasesPractice.tsx:59-66`, which does). Navigating
away or advancing the deck mid-recording leaves the mic indicator lit until
the 5s timeout, and the late `onstop` then scores the *previous* card's word
and lands it as state on the card now on screen.

### D4 — WITHDRAWN: `sseChat` on abort — not a defect

**This item was wrong and is retracted.** It is kept rather than deleted
because the reasoning that produced it is easy to repeat from the docstring
alone, and the next reader deserves the refutation rather than the trap.

What it claimed: `sseChat.ts:88-155` has no `try`/`finally` around the read
loop, so on abort `reader.read()` rejects, `finishContent()` at `:153` is
never reached, and — since the docstring at `:38-46` tells callers to drive a
spinner off `onContentComplete` rather than the resolved promise — an aborted
reply leaves the composer locked.

Why that is wrong. Both callers clear their own state in a `finally` on the
promise and do not depend on `onContentComplete` firing:

- `ConversationSimulator.streamReply` has a plain `finally { setSending(false) }`.
- `ChatTab.send` calls `setLoading(false)` in `onContentComplete` — that is
  the "composer reopens with the last word, not with the review"
  optimisation the docstring is actually about — **and** again in a guarded
  `finally` (`ChatTab.tsx:267-277`).

The one case where the composer does stay locked after an abort is
deliberate, and that `finally` block's own comment says so: an abort only
happens because a *newer* `send` called `abortRef.current?.abort()`, so the
newer request owns the composer and the older turn must not unlock it.
Unlocking there was a real bug once — it let a third question abort the
second mid-sentence — and the guard is the fix.

The suggested direction was also harmful: firing `onContentComplete` on
abort would mark a partial reply as complete and persist it to history.

Residue, not worth an item: the mid-stream `SseChatError` at `:135` returns
without an explicit `resp.body.cancel()`, so that reader lock is released by
garbage collection rather than promptly. On the abort path the fetch
machinery tears the body down itself, so nothing leaks there.

The CLAUDE.md invariant does hold, as originally stated: the loop reads past
`[DONE]`, post-terminator deltas are dropped, and app frames after it are
delivered.

*Raised by the Codex review bot on #381 and verified against the callers
before withdrawing.*

### D5 — `reviewQueue` loses ratings silently — domain logic — CONFIRMED

`reviewQueue.ts:47-69`. `enqueue` returns a fully-formed `QueuedRating` even
when `safeWrite` threw, so the caller reports the rating queued and it is
gone — and an extended offline session is exactly what fills the quota that
causes the throw. One malformed byte in the key discards the learner's
**entire** pending queue rather than one entry. `reviewQueue.test.ts:187-220`
asserts only that these paths do not throw, never that data survived.

### D6 — `useAdminAuth` leaks its auth listener — frontend — CONFIRMED

`useAdminAuth.ts:24-71` assigns `subscription` *inside* an async `init()`,
after `await getSession()`. The effect's cleanup runs synchronously and sees
`null` whenever the component unmounts first — StrictMode's double-mount, or
any fast navigation. The listener is then orphaned and never removed.
`useAuth.ts:11-40` has the correct shape.
